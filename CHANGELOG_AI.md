- Measured first with a per-stage timer copy (`tmp/tt-sim/pgd_prof.py`, 60 s 1080x1920 excerpt, 1801 frames, 121.6 s total): `prep` (read + yuv→rgb + downscale) 1.68 s, the attack loop 96.23 s, `return` (rgb→yuv + numpy) 7.15 s, wait-for-decode 0.67 s, write-to-encoder 1.33 s. The attack is ~79 % of the wall clock; everything FFmpeg does at full resolution (decode + NVENC qp18 encode) is only 10 s of the same clip. The transport theory was wrong.
- Behaviour: `pgd_clip.py` gained `--amp off|bf16|fp16` (default `off`) and `--adaptive-skip <mean-abs threshold>` (default 0). The per-step similarity now comes from the embedding the step already computed, and the reported `sims` is recomputed once per group from the delta that is actually written.
- Measured (16.46 s 1080x1920 clip, post-TikTok-sim CLIP — lower is further from the original): shipped strong 0.9048 / 0.9087 (1080p / 720p) in 45.4 s; new code, strong + bf16 0.7837 / 0.7964 in 31.8 s; strong + bf16 + `--frame-step 2` 0.7899 / 0.7992 in 26.6 s. Same-strength check: bf16 vs float32 in-attack mean CLIP 0.7109 vs 0.7095, so precision is not the source of the gain — removing the early stop's one-step lag is, and the frames now spend their full step budget inside the same eps bound. `--adaptive-skip 0.004` reused only 3 % of frames on a cut-heavy movie clip, so it is a content-dependent extra, not a default. 5 and 8 steps land within noise of each other, so 5 is enough.
- Files: `pgd_clip.py`, `CHANGELOG_AI.md`, `PIPELINES.md`, `AI_INTEGRATIONS.md`.
- Validation: `npm run validate` (handoff 49 checks, 170 unit tests, server syntax 25 files) after the patch, plus a default-path run with no new flags. All scratch media lives in gitignored `tmp/tt-sim/`.
- Remaining risk: the flags are not wired to the app yet (no UI toggle, and `runPgdClip`/`pgd_server.py` do not forward them), so nothing changes for an operator until that lands. The strength numbers are from one 16.46 s clip; a 5-minute clip still costs ~6.5-7 min of PGD on this 35 W GPU, so the "many long videos" case is still bounded by this hardware.
- Two concurrent PGD processes were measured on the same box and are NOT a throughput win: on the 60 s excerpt one worker took 80.9 s; two workers took 191.2 s for the same pair of clips (2.36x slower per clip, ~15 % worse total throughput). Peak VRAM reached 3932/4096 MiB, temperature 84 C, the GPU stayed on its software power cap (throttle reason 0x4) at ~30 W with SM clock 1245 -> 1363 MHz, and GPU utilisation only moved 70 % -> 78 %, so the two processes mostly steal the same power budget. This is the mechanism behind the old "two ViT-B-32 on a 4 GB card hung for ~90 minutes" note. Frame-step beyond 2 also stops paying: post-re-encode CLIP 0.7917 at step 2, 0.8547 at step 3 and 0.8235 at step 4 against 0.7901 at step 1, so step 2 is the sweet spot.
- The three remaining speed levers were also measured on the same 60 s excerpt (baseline bf16 + frame-step 2 + 3 EOT views: 72.6 s, i.e. 1.67x faster than the original 121.6 s): (1) merging the PGD write encode into the Unique encode is worth nothing - a variant that consumes the frames with no encoder at all (`tmp/tt-sim/pgd_null.py`) ran in 72.4 s, so the second encode is already fully overlapped with the attack; (2) dropping EOT from 3 views to 2 gives 25.0 s (-6 %) but post-re-encode CLIP slips 0.7917 -> 0.8077, and the paired frame-step-1 run came out at 0.8294, i.e. the gain is inside cross-run noise and costs strength; (3) fp16 is identical to bf16 (26.6 s vs 26.7 s, 0.7942 vs 0.7917) because Ampere runs both at the same tensor-core rate. `torch.compile` cannot be used on this host: inductor needs Triton and there is no official Windows build ("Cannot find a working triton installation"), so `--compile` now traces once at startup and falls back to eager instead of killing the job. The only untested lever left is a genuinely smaller surrogate (open_clip 3.3 lists MobileCLIP-S0/S1/S2), which needs its own input size and normalisation plus a transfer check - a cheaper surrogate may transfer worse than the model being attacked.
- Follow-up on those two: `triton-windows 3.8.0.post29` installs on this host, but `torch.compile` still fails with "Failed to find C compiler" - the machine has no MSVC/clang/gcc and no CUDA toolkit at all, so inductor cannot build a kernel. Making it work needs Visual Studio Build Tools (multi-GB) before any speedup is provable, on a GPU already capped at ~30 W. The smaller-surrogate question was then answered by measurement instead: MobileCLIP2-S0 (74.8 M params, 256 px, mean 0/std 1) was wired into a scratch copy (`tmp/tt-sim/pgd_mob.py`) and run with the identical attack settings against ViT-B/32 on the same clip. It was **not faster** (30.0 s vs 26.9 s; the 256 px input offsets the smaller parameter count) and the perturbation **transferred badly**: measured by the independent ViT-B/32 harness after the platform re-encode, the MobileCLIP attack lands at similarity 0.9761 / 0.9795 (1080p / 720p) against 0.8474 / 0.8467 for the ViT-B/32 attack, i.e. close to the 0.998 control - the attack only moves the embedding it was optimised against (its own in-attack mean read 0.6973). Do not swap the surrogate down: it costs strength and buys no time.

## 2026-09-25 — Unique wobble (±N°, 1.5s) beside the static tilt
