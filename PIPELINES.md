# GhostForge pipelines

This document is a navigation guide, not a replacement for code. Read only the section relevant to the task.

## 1. Unique

Frontend queue (`processOneFile` / `startProcessing`) -> `POST /api/upload` -> job registry -> `GET /api/stream/:jobId` SSE -> backend video processing -> compare/download/export.

Progress events (`{ type: 'progress', value, phase }`) may also carry `etaMs` - the estimated remaining time for that phase, used by the two Unique bars. The unique value comes from FFmpeg's own `speed=` reading (fallback: wall clock) and is withheld until the encode passes 3%, because the first reading happens while the filter graph is still starting and is far too slow. The PGD value comes from the `frame i/n` counter `pgd_clip.py` prints, measured against the wall clock. The field is optional and additive.

Unique shares job/SSE and FFmpeg infrastructure with other features, but its processing behavior should be treated as independent. Do not change it as collateral cleanup for Edit/Reframe work.

Unique output lifecycle: `job.outputPath` (`<jobId>_output.mp4`) plus `<jobId>`-prefixed sidecars in `uploads/` (`_enc.mp4`, `_pgd.mp4`, `_sized.mp4`, `_cmp_orig/_cmp_proc/_cmp_diff.jpg`, `_clip.json`). When that pipeline is about to emit `done`, `server/unique-hold.js` records the job in `uploads/unique-hold.json` (display name, source name, result stats). A restart loads that list back into the job map and the Unique Completed list. Save removes the record after the copy is in the operator's folder. Remove deletes the record and the file. A job that died before `done` is not restored. `DELETE /api/job/:jobId` removes the output, the tracked input when it is not `keepInput`, and every sidecar. Cancel must stay able to kill the metadata remux as well as the main encode. After the metadata remux the backend stores a perceptual estimate from three matched content moments of source vs output. It grabs two frames per side per moment - 17x16 for the documented dHash, 64x64 for the two newer measures - and reports three independent numbers: a 17x16 (256-bit) dHash bit distance (`perceptualDistance`, `perceptualWorst`, `perceptualBest`, `perceptualFrames`), a 63-bit DCT pHash distance (`perceptualPHash`, `perceptualPHashWorst`) and the mean/worst cell of a 4x4 dHash grid (`perceptualBlockMean`, `perceptualBlockWorst`), plus a mean absolute luminance delta on the same frame pairs (`perceptualLumaDelta`, `perceptualLumaWorst`). The dHash number is deliberately unchanged so readings recorded before 2026-09-25 stay comparable; it saturates near 40%, which is why the pHash and grid numbers exist. All of them are operator estimates, not a platform dedup verdict and not CLIP similarity; `enablePgdOnly` jobs do not produce them.

Edge check (quality guard): the same job also runs `measureSeamProfile` over 5 matched moments and stores `seamIn` / `seamInRowPct` / `seamInFrames` (the file that went in) and `seamOut` / `seamOutRowPct` / `seamOutFrames` / `seamFrames` (the render). A seam is a *discontinuity*: one row jumping at least 25/255 beyond its neighbours and at least 3x their largest jump, so a steep but continuous content edge is not a seam. `seamVerdict` classifies `none` / `source` / `added`, and the pipeline is only blamed when the output has a seam the input did not. This exists because the hashes are frame averages and can read HIGHER while the picture gets worse: a real regression measured dHash 39.7 / pHash 28.0 on a render with a hard seam across the whole frame, versus 40.0 / 27.5 on the clean render of the same clip.

Unique strength: the `uniqueStrength` setting (`light` / `standard` / `strong`, default `strong` in the UI, `standard` when the field is missing) scales the zoom, stretch, shake, reframe, lens, tempo, colour, grain and audio gains through `UNIQUE_STRENGTH`. `standard` is gain 1, i.e. the pre-2026-09-24 ranges.

Unique rotation: `uniqueRotate` (degrees, 0 disables, UI default 1) tilts the frame before the canvas fit, so the tilt never rotates a black pad, and then zooms by exactly what a tilt that size needs (`cos + (H/W)sin`, plus a 0.012 margin). The margin matters: at an exact fit the window corners sit tangent to the rotated edges and a tangent pixel samples half outside, which shows as a dark corner. A tilt costs a little extra edge and softens caption outlines (about +14% / +19% / +23% dHash at 1 / 2 / 3 degrees on a captioned test frame).

Unique tempo is a base speed, one direction for the whole clip, plus an 8-second curve from `server/tempo-curve.js`. Strong uses the measured shape 1.15, 1.15, 1.12, 0.90, 0.88, 0.87, 1.00, 1.00 multiplied by the base speed. Lower strengths take a fraction of that shape. Extreme does not go past the strong shape. Video `setpts` and audio `atempo` use the same slice speeds. On the 8 s excerpt the streams ended 35 ms apart, about one frame. The panel still maps with one speed, the harmonic mean, so it does not line the curve's moments back up.

The audio chain is one `atempo` slice per source second. When the full FFmpeg argv would pass `WINDOWS_COMMAND_BUDGET` (24000), the video filter still runs as one command and the same slice text is rendered in chunks (`chunkTempoBranches` / `tempoAudioChain`), then muxed. FFmpeg 9 on this machine has no `-filter_script` or `-filter_complex_script`. A shorter clip stays one command, so its filter text does not change. Spill files are `<jobId>_aspill_*` and are removed when the attempt ends and on `DELETE /api/job/:jobId`.

Unique pause: while a queue is running, Tạm dừng calls `POST /api/unique/pause/:jobId` with `{ paused: true }`. That freezes the current Unique child (encode, PGD, or the metadata remux) with `NtSuspendProcess` and stops the queue from taking the next clip. Tiếp tục resumes the same process. Cancel still kills the job, including one that is frozen. Edit and Reframe are not paused by this route.

While that run is going, the Unique drop zone and file picker stay open. A video dropped there, or a YouTube file sent to Unique, joins the same claim list and runs after the clip already taken, with the settings from the Start click. Tạm dừng still holds the next claim. The X on a clip that has not started removes it. Reorder stays off until the run ends. The settings panel stays locked for that run.

Optional steps, each with its own switch, default off. A switch that is off skips that step. The order is Smooth, then the existing Unique encode, then PGD, then burned-in word captions. Smooth is `realesr-animevideov3` from `tools/realesrgan/` (`GHOSTFORGE_REALESRGAN` overrides the folder). A frame whose short side is already at least 1080 stays that size and uses a light hqdn3d and cas pass. A smaller frame, or Smooth set to AI, still uses `realesr-animevideov3` (scale 2 when the long side is at least 1080, otherwise scale 3) and is fitted back to the source size, so Unique and PGD do not receive a 4K frame. The Unique log names the preset that started the run. No preset means the open panel switches. The model path reports Làm mịn as each output frame is written, instead of once per 240-frame chunk. Captions sit in the middle or at the bottom. The bottom line is inset by 10% of the frame height. Middle stays centred. A saved top place becomes middle. Cancel on Unique releases that run at once, so a later clip sent from YouTube starts instead of waiting on the cancelled run. A finished clip that came from YouTube shows that origin and the preset name chosen on the YouTube tab when it was sent. The ncnn process takes `withGpuExclusive`. The Unique encode stays outside that lock and its filters, tempo, grain and encoder choice are unchanged. Unique still adds its own grain after Smooth. On a real face the video model can redraw skin. Smooth failure stops the job before Unique. Captions run on the file after PGD, because Unique retimes the audio. `caption_words.py` (faster-whisper small, CPU int8, `.venv-diar`) detects the language and the word clock. Google `speech:recognize` then uses that language (`pt` becomes `pt-BR`). The burn keeps the local clock. A Google word replaces the local spelling only when `alignCaptionWords` calls them the same beat. Google's own word times are not burned. The picture is one word at a time, Arial Black, white, black outline, centred. A caption failure keeps the Unique file. PGD failure still keeps Unique. The built-in Unique preset select is gone. A named preset in the browser stores those switches. The saved names are one dropdown. Sửa loads one preset onto the panel and Lưu lại overwrites that same preset. A toast confirms Tạo preset and Lưu lại. A name already used by another preset is refused. Edit, Reframe, and YouTube can start Unique with one saved preset when the queue is idle. A clip that arrives while Unique is already running keeps the settings of that run.

Unique geometry is always ONE uniform transform for the whole frame, zoomed about the frame centre. The old content-island overlay magnified only the detected band, so on a source whose blurred bars are part of the same scene the picture broke at the band edges (bigger inside, smaller outside); moving the crop to follow the island shifted the whole picture by about 9% of the frame height, which the operator reads as "the image moved", so the crop stays centred. Do not reintroduce a per-region overlay or an off-centre crop here.

The `Content-Aware` toggle and the content-island scan it used were REMOVED on 2026-09-25. They only ever changed the zoom tier by about 1%, blocked the tilt on a guessed basis, and fed a blur-bar auto-detect that keyed on content edges; the operator judged the toggle not worth the rule it added. `detectContentIsland` still exists because the Auto Reframe pipeline uses it. The blur-bar `featherTop` / `featherBottom` fields are now the only bar-aware feature and they act purely on the entered percents.

Blur-bar seam softening: when the source has *static* bars above and below the picture, `featherTop` / `featherBottom` (percent of the frame height) cross-fade the frame into a vertically blurred copy over 56 px centred on each bar edge, before the uniform transform. Both fields must be greater than 0; there is NO automatic edge search any more (`detectBarBoundaries` was removed on 2026-09-27 with the other dead helpers - it keyed on content edges and could blur a stripe across a face). With the switch on and both percents at 0 the run logs `Blur-bar seam ON but no percents entered - nothing done`. The mask must come from the video stream (`split=3`), never from a `color=` source. These fields do NOT fix Edit contain/fill output, where the picture window follows the speaker.

Anti-repeat between jobs: two signatures of the last Unique job are kept in process memory and re-drawn while a new job's signature is within noise of them (six attempts each): the visible grade/shake (`lastUniqueSignature`, tolerance `[0.15, 0.6, 0.012, 0.012, 0.006, 0.010]`, log `Anti-repeat: re-drew grade/shake`) and, since 2026-09-28, the audio EQ-drift depth/periods (`lastAudioSignature` = `[driftLow, driftMid, driftHigh, periodLow, periodMid, periodHigh]`, tolerance `[0.02, 0.02, 0.02, 0.8, 0.8, 0.8]`, log `Anti-repeat: re-drew audio drift Nx`). This exists because the per-job draw is independent, so a batch could otherwise repeat the same warmth/contrast/grain or the same drift rhythm. Both are per process - a restart resets them - and neither touches geometry or tempo. The audio guard is a rare safety net: the draw ranges are wide, so consecutive jobs usually differ on their own.

PGD (`enablePgd`, levels light/medium/strong/extreme plus the `visible` test level): the attack always runs on CUDA through `pgd_clip.py` (CLIP ViT-B-32 + EOT jpeg/resize views, `--eps/--steps/--alpha/--target-sim` from `PGD_LEVELS`), then the attacked frames are written back by a second FFmpeg process. That write-out pass now follows the operator's Encoder choice: `runPgdClip` resolves it with `resolveEncoder`, smoke-tests it with `canOpenEncoder`, and passes `--enc-args` (JSON) + `--enc-label` to the script (`h264_nvenc -preset p5 -rc constqp -qp 18`, `h264_qsv -global_quality 18`, or `libx264 -crf 16`). Quality stays deliberately high because the perturbation is only a few luma levels. Expect a PGD output much larger than the source (measured 1.7 MB -> ~6.3 MB on a 4 s clip) and do not try to fix that with the encoder: the size comes from the frame-varying perturbation, and qp18/21/24 all land at ~6.2-6.35 MB. Shrinking it means erasing part of the attack (crf28 -> 1.49 MB, decoded CLIP sim 0.9212 vs 0.9119 at high quality; source = 1.0000). `enablePgdOnly` skips Unique entirely and only then runs the shared post-render measurement.

Measured 2026-10-01 (TikTok-like re-encode ladder, see `docs/transcode-robust-unique.md` §8b): raising the PGD level from medium to strong is the one lever that pays — about +4.7 points of surviving CLIP distance at the same wall time (67-71 ms/frame at either level, because the frame pipeline dominates the attack). The opt-in `--eot-mode mix` / `--pool-size 8` variants gain only 0.7-1.0 point and lose that gain when PGD runs on top of a Unique render, so they stay off. Do not expect PGD to defeat a hash-based match: it moves pHash 0.26% where the Unique geometry/grade/tempo layer moves it 34.9%.

Measured again the same day with a per-stage timer: the attack loop, not the frame transport, is the cost (96.2 s of 121.6 s on a 60 s excerpt; everything FFmpeg does at full resolution is 10 s). The shipped per-step early-stop check spent an extra forward pass per step on the candidate AFTER the update, so frames were being retired one step early and the attack was quietly short. `--amp bf16` (opt-in, and it does not change the result: in-attack mean CLIP 0.7109 vs 0.7095 in float32) plus that corrected check gives, on the same 16.46 s clip, **0.7837 / 0.7964 post-re-encode CLIP in 31.8 s against the shipped 0.9048 / 0.9087 in 45.4 s** - stronger and ~30 % faster. Adding `--frame-step 2` reaches 26.6 s for 0.7899 / 0.7992, a 0.8-point cost for another 16 %. `--adaptive-skip` (reuse the previous perturbation when the 224px picture barely moves) only touched 3 % of frames on a cut-heavy clip; it is for static talking-head footage, not a default. **Since 2026-10-01 the app sends `amp: bf16` and `frameStep: 2` on every PGD request** (`runPgdClip` -> `pgd_server.attack_argv`), so this speed is live once the app is restarted; `pool-size`, `adaptive-skip`, `phash-loss` and `--compile` remain off, and the Unique tab defaults to the `strong` level.

Do not trust the `--enc-label` alone: it is printed from the argument even when the encoder falls back (a local `import json` inside `main()` once made every run fall back to x264 while the log claimed NVENC). The script now logs `[codec <name>]` taken from the parsed args, and an invalid encoder fails the run. Measured after the fix: NVENC qp18 and x264 crf16 are identical in wall time (31.5 s), size (11.51 vs 11.50 MB on 8 s) and quality (decoded CLIP sim 0.9124 vs 0.9116) - pick the GPU encoder to free the CPU during the attack, not for speed. `--hash-loss` (soft 17x16 dHash term added to the CLIP loss, default 0) was measured to cost nothing and change nothing (dHash 3.5% -> 3.7-3.9%, pHash flat) because a sub-visual perturbation averages out at 17x16; leave it off.

PGD backstop textures (dead-zone fill + face/skin carrier) are capped sub-visual: `floor <= 1.2/255` and `face_amp <= 2.0/255` regardless of `eps`. They used to scale with eps, which at strong/extreme (eps 10-16) painted a visible 28-40 px plaid over flat areas (measured 16 px column-profile peak 0.34 vs 0.12 after the cap). Do not scale them with eps again - if a stronger attack is wanted, raise the level's steps/eps, not the backstop. Cost of the cap: decoded output vs source went 0.8895 -> 0.9201 at strong (the texture was part of the distance); in-attack CLIP did not move.

PGD loop performance: never call `.item()` (or `float(tensor)` on CUDA) inside the per-step loop - each call syncs the device and cost 0.108 s per call in a cProfile run. Frame I/O uses one preallocated buffer with `readinto`, and per-group similarities are read with a single `sims.tolist()`. Measured 32.2 s -> 28.8 s per 240 frames at strong. The per-frame early stop (a frame that reaches its target stops being updated, `active` mask) is a guard for clips where only some frames are hard; it changes nothing when the whole group converges early.

PGD frame transport: the decoder writes **yuv420p** and the encoder reads yuv420p (3.1 MB per 1080x1920 frame instead of 6.2 MB for rgb24); `pgd_clip.py` converts with `yuv_to_rgb` / `rgb_to_yuv` on the GPU using BT.709 limited range. If you touch those commands, keep the explicit colour tags (`-color_range tv -colorspace bt709 -color_primaries bt709 -color_trc bt709` on the rawvideo input AND on the output) - raw yuv420p has no implicit tags, and without them the render is written as `unknown/unknown`, which makes every later conversion (grayscale grabs, PNG, re-encode) free to pick a different range (measured 34.5 dB PSNR / 2.8% luma error without tags, 49.5 dB / 0.1% with them). Speed: 28.8 -> 24.6 s per 240 frames at strong, the attack unchanged (in-attack CLIP 0.8583, decoded output vs source 0.9230).

Chroma grain is capped at 2 in the Unique noise filter for every strength (`chromaN = min(2, ...)`) - at "Cực mạnh" it used to reach 3 and the coloured speckle dominated the render; luma grain still scales with the strength. Do not raise the chroma cap without a visual check on a real clip.

Audio fingerprint protection (measured 2026-09-28 with AcoustID `fpcalc.exe` - ffmpeg here has no chromaprint; the tool lives in `tmp/tools/` and `tmp/tech-tests/fp-real.mjs` does the comparison): the Unique audio chain already removes essentially all of the source's sub-fingerprints. Reference on an 8 s clip: unrelated clip 0.0%, plain AAC 96k re-encode 60.5%, EQ only 41.9%, EQ+allpass+compressor+stereo 11.6%, `atempo=0.9885` alone 11.6%, full chain 0.0%, full chain + another AAC 96k 2.3%. Keep this in mind before adding more audio "protection": the cheap EQ/compressor/tempo already do the work, and the picture side is the one that needed the extra passes (PGD). A hand-rolled peak-pairing proxy is NOT a substitute - it scored an unrelated clip at 97%.

Two remaining PGD ideas were measured and rejected as defaults (2026-09-28). `--frame-step N` (default 1) attacks every Nth frame and copies the leader's perturbation to the frames in between: 21.7 s -> 17.7 s per 240 frames at step 2 (-18% only, because the ~17 s frame pipeline dominates the ~4.7 s attack), and the effect that survives a harsh crf 30 re-encode slips from 0.9323 to 0.9351 (~4% of the effect), so it is a real trade, not a free win - leave it off unless a special case needs the time. Warping along optical flow (OpenCV Farneback at 1/4 scale + `remap`, 47 ms/frame) is not damaging at small alpha but also nearly pointless: alpha 0.15-1.0 moves dHash only 2.5-5.1% and CLIP 0.9-3.0%, against ~30% dHash from the zoom/grade that is already in the chain. The picture side is at its practical ceiling on this hardware.

PGD speed: frames are attacked in groups (`--batch`, default 8) because they are independent - each keeps its own phase (`frame_i * 1.9`), its own delta and its own loss term, so grouping changes only how many share a forward/backward call. Measured on an 8 s clip at the light level: 35.4 s (batch 1), 32.6 s (4), 28.2 s (8), 28.1 s (16); in-attack mean CLIP 0.9202 vs 0.9205 and decoded output vs source 0.9112 vs 0.9118, so the attack is not weakened. A group that exhausts VRAM halves the batch, logs `VRAM ran out — batch size N frame(s) per pass` and retries the same frames down to 1 - keep that path working if you touch the loop. The encoder choice does not change PGD speed (x264 28.3 s vs NVENC 28.2 s at batch 8).

Two further speed steps leave that attack untouched. `withGpuExclusive` in `ghostforge-server.js` lets Unique encode stay parallel, but `runPgdClip` and `measureClipSim` take the GPU one at a time. A second PGD logs `[PGD] Chờ GPU` and waits. Two ViT-B-32 models on the 4 GB card were the runs that sat for about 90 minutes and stopped with a short PGD file. Inside one pass, `pgd_clip.py` decodes the next frames on a side thread and writes the previous group while the current group is attacked (`decode and encode overlap the attack`). eps, steps, EOT and phase are the same calls. As of 2026-10-01 the loss is computed on the pool-4 residual that is written, and the full-frame carrier is not added. `runPgdClip` asks the long-lived `pgd_server.py` first (one ViT-B-32 for the whole server run) and falls back to a one-shot `pgd_clip.py` if that process is down. A second clip logs `[PGD] nóng: dùng model đã nạp`. `--frame-step` stays off: it is faster and it weakens the attack. Measured 2026-09-30 on this RTX 3050 Laptop, one 8.000 s 1080x1920 30 fps clip (240 frames), batch 8, EOT 3, NVENC constqp 18, wall clock of the whole `pgd_clip.py` process (CLIP load included): medium 21.91 s, in-attack mean CLIP 0.8908, skip 0; light 21.11 s, mean CLIP 0.9101. Neither run logged `VRAM ran out`. The 2026-09-28 light batch-8 number of 28.2 s used EOT 4.

The per-frame phase step matters for how the backstop texture LOOKS: at 0.21 rad/frame it crawls with the picture and the eye tracks it (frame-to-frame correlation of the texture measured 0.829 against 0.755 for the source), which the operator reads as stripes; at 1.9 rad/frame it decorrelates (-0.139) and reads as noise, with the same amplitude, the same decoded CLIP distance and +0.5% file size. Do not slow it back down without a temporal check (`tmp/tech-tests/temporal-scan.mjs`). EOT views: `runPgdClip` passes 3 - measured neutral against 4 (decoded distance 0.9196 vs 0.9228, harsh-re-encode 0.9381 vs 0.9408) and ~6% faster.

Lớp nhiễu nhẹ (`enableAdversarial`, default ON, UI `Lớp nhiễu nhẹ (không phải PGD)`): adds only cheap perturbations - a hue wobble, `chromashift` +/-1, extra grain and a slightly stronger base geometry. It used to push a `geq` stripe layer (amp 6.0-10.5 luma, 28-40 px sine stripes) whenever PGD was also on; that layer was REMOVED on 2026-09-28 because it painted visible vertical bands over the whole frame and cost 3-5x the render time (`geq` is single-threaded): 33.7 s -> 26.2 s on a 4 s clip. Do not reintroduce it - use `pgdLevel` when the attack needs to be stronger. The `geq` filters that remain in `ghostforge-server.js` belong to the blur-bar mask and the Edit contain/fill alpha masks.

Semantic measurement (`clip_sim.py`, called from `measureUniqueOutput`): every Unique job - PGD or not - decodes 12 frames at 3 fps from the source and the render, embeds them with ViT-B-32 and reports `clipSimOut` (plus worst frame, frame count and device) with one `[SYS] CLIP sim nội dung` line and a panel row. It is local GPU work (~4-8 s), no API, 240 s timeout, and a failure is a logged skip. Read the number against the calibration measured with this exact method: identity 1.0000, Unique Light 0.9454, PGD-only light 0.9121, Unique Strong 0.8798 - a plain Strong pass moves the embedding more than a light PGD pass, so this row is not a ranking of strength. It is also a different number from `clipSim`, which is PGD's own in-attack average.

The four measurements in `measureUniqueOutput` (perceptual hashes, seam check, audio, CLIP) run at the same time via `Promise.all`; they only read the two files, so their log lines arrive in completion order. Measured on an 8 s clip the whole stage is ~6 s and the CLIP step alone ~5.3 s, most of which is fixed overhead (`python` + `import torch, open_clip` 3.0 s, model load 1.7 s, frames 0.6 s). Keep that in mind before adding a fifth measurement to the same stage: it would hide behind CLIP only if it is cheap.

That CLIP overhead is now paid once per server run instead of once per clip: `clip_sim_server.py` is a warm helper (ViT-B-32 loaded at start, JSON requests on stdin/stdout) and `measureClipSim` prefers it, falling back to the one-shot `clip_sim.py` on failure/timeout. Measured on an 8 s clip: measurement 6.5 s cold, 1.8 s warm; whole job 13.0 s -> 6.6 s. Before a PGD pass `prepareClipWorkerForPgd` asks the helper for free VRAM: with >= 2000 MB free (`CLIP_PGD_VRAM_HEADROOM_MB`) it stays loaded and only logs `CLIP helper giữ nguyên trong lúc PGD (còn X/Y MB VRAM trống)`; below that it answers `cmd: "unload"`, drops its weights (keeping the process and torch) and reloads lazily afterwards. If the control request fails the helper is stopped, which is the old behaviour. Measured: resident -> PGD 28.4 s + measurement 2.3 s; unloaded -> 28.3 s + 3.3 s. The helper is killed on server exit and holds VRAM while the app is idle.

Stage timing: the handler stamps `tProbe` (hash + probe), `tEncode`, `tPgd`, `tMeta` and `tMeasure`, logs `[SYS] Thời gian: ...` before done and returns `stagePrepMs` / `stageEncodeMs` / `stagePgdMs` / `stageMetadataMs` / `stageMeasureMs`. The stages do not cover the small tail after `tMeasure` (compare frames, SHA-256, re-probe, ~0.1 s), and upload time is not included because it happens before the stream starts. Both paths (normal and PGD-only) set them; PGD-only reports `stageEncodeMs` 0.

Unique audio (both the change and its measurement): the audio chain is a static random EQ (6 bands) + allpass + `acompressor` + stereo tools, then an `acrossover=split=400|3500:order=4` split whose three bands each get a slow per-job gain cycle (`volume='1+amp*sin(2*PI*t/period)':eval=frame`, amplitude scaled by `gstr.audio`), summed back with `amix=inputs=3:normalize=0`, then the 9-15.5 kHz hiss mix and `volume='1+0.014*gstr.audio*sin(2*PI*t/7)'`, `atempo` and `aresample`. The crossover is a Linkwitz-Riley split, so with every band at gain 1 it is level neutral (measured -0.14 dB, 0.11 dB/s) - do not swap it for band-passed `asplit` branches (crossover dips at the crossover points) or for `equalizer` + `asendcmd` (an instant gain step can tick). After the metadata remux the job measures the audio the same way it measures the picture: `grabAudioPcm` pipes mono 16 kHz PCM from both files and `server/audio-profile.js` (pure) reports per-second loudness and per-second three-band energy, aligned by the `speed` retime factor, as `audioLevelDeltaDb` / `audioLevelDriftDb` / `audioBand*Db` / `audioBandDriftDb` / `audioClickRatio`, with one `[SYS] Audio đo được` log line. Capped at 120 s because every drift period is a few seconds, and it is an operator estimate - never a platform audio-fingerprint verdict, and not comparable across different content.

Post-render measurement is ONE shared path: `measureUniqueOutput` (picture hashes, seam check, audio, plus a deleted crf 30 long-side-720 proxy measured as `harshDistance` / `harshPHash` / `harshClipSim`) plus `uniqueMeasurementStats` for the `done` fields. The proxy filter lives in `server/harsh-scale.js`. The log line is `[SYS] Sau nén`. Failure of that proxy leaves the harsh fields null and the job still succeeds. Both the normal Unique path and the PGD-only path call it, so a PGD-only job reports the same numbers as any other job - it used to skip all three and its result panel came out empty. PGD-only does not retime, so it measures with `speed` 1, and the call has to stay BEFORE the source file is unlinked. If you add a fourth measurement, add it inside `measureUniqueOutput`/`uniqueMeasurementStats` rather than in one branch.

Two of those rows are now opt-in behind `job.settings.enableFullMeasure` (UI toggle under HIỆU NĂNG, default off): the CLIP embedding row and the harsh 720 proxy. They are the only parts that need the GPU and a whole-file re-encode, and because `measureClipSim` takes the GPU lock AFTER `runPgdClip` has released it, a finished job used to wait for the other worker's PGD - measured on a real 9-clip batch: 2m25s, 3m52s and 5m24s of waiting, ~11m40s in a 25-minute session, while the cheap rows only cost seconds. Perceptual hashes, the seam quality guard, audio and the stage timers always run. The two rows read `đang tắt — bật "Đo đầy đủ" nếu cần số này` when the switch is off, which is expected, not a failure.

## 2. Edit

Topic routing runs BEFORE the plan: unless the operator pins a topic in the Edit tab, `classifyVideoTopic` looks at 3 stills (one small call on the safe model ladder, ~2.5 s) and `resolveTopic` applies that topic's workflow only when the label is known and confidence >= 0.6 - otherwise everything stays generic. The profile addon from `server/topic-profiles.js` is appended to BOTH the global-plan prompt (how the video is split into parts) and the per-part Detail prompt (how the 9:16 frame is chosen), and the topic is stored with the part scores.

STT and diarization run on a concatenated "keep" file of the parts that will actually be rendered, not on the whole source: `[EDIT] STT gọn: chỉ nghe Xs trong Ys (bỏ Zs không dùng)`. The plan is re-timed onto that timeline for the speaker mapping and the speech lines are split back per part. If the keep file cannot be built the stage falls back to the whole-file listen and says so.

Each finished run also produces a summary (log line + a card in the Edit tab): source name, topic, total duration, kept seconds, part count, per-part row (timecodes, duration, the clock time it finished, QA score) and the dropped stretches with timecodes and total.

After rendering, the focus path grades itself (`server/edit-qa.js`): up to 30 local samples (no API) ask whether a subject peak sits inside the crop window, whether the crop is pinned to a frame edge, whether the frame is empty/dark and how long the crop held one position, plus how much of the part the AI actually covered. The result is a 0-100 score with a grade and warnings, logged as `[QA] Chất lượng part: …`, shown under each part in the Edit cut table, and appended to `uploads/edit-qa-history.json` (last 500, gitignored). `GET /api/edit/qa-history` returns the last 100 entries plus per-mode averages, and each run logs `[QA] N part · điểm trung bình X/100 · …`. This is a smoke detector, not ground truth: it flags parts worth watching, and it is the measurement layer any later auto-tuning has to be built on. The same finished part is also recorded in `uploads/edit-hold.json` before `part-done` (`server/edit-hold.js`). A restart loads `GET /api/edit/held` back into the cut list so Save still works. Save and Clear drop that record. A part that dies before the mp4 exists is not restored. The uploads folder is not scanned.

When that score is under 80 the part gets an automatic second pass (`criticFocusAim`), with no operator input: up to 4 still PAIRS at the moments the local check disliked (SOURCE frame + the 9:16 render of the same moment) go to a vision model, which answers only "is the main subject fully inside this crop, and if not where is it in the source frame". The corrected aim is applied (`applyAimOverrides`), the part is rendered again to `<file>.critic.mp4`, the same local check grades it, and the better file is kept - the model never decides alone. The critic runs on the measured-safe ladder (`gemini-3.5-flash-lite` first): the first live attempt on the UI model returned HTTP 503, and the shared overload memory applies here too. A part already scoring >= 80 costs nothing extra, and a critic failure is logged and skipped rather than failing the part.

Focus 9:16 (`composeFocusClip` in `ghostforge-server.js`, graph from `focusFrameGraph` in `server/ffmpeg-expressions.js`): the canvas stays 1080×1920. A focus window crops the largest 3:4 box in the source (810×1080 on 1920×1080), scales it to 1080×1440, and centres it on a blurred copy of the full frame, so the top and bottom are a soft letterbox. The plan's `frames[]` carry `focus` (one main subject or action fills the frame - the default), `pip` (main subject still fills the frame plus a small corner window for a second event) or `split` (top/bottom halves, main subject on top, second event below). `cx,cy` is the main subject in the SOURCE frame, `cx2,cy2` the second event; a pip/split window without `cx2/cy2` degrades to a plain focus window (`parseFraming` deliberately does NOT default them to cx/cy). The focus crop is `crop=W:H:x=EXPR:y=EXPR,scale=1080:1440` with W:H the largest 3:4 box inside the source (810×1080 for a 1920×1080 source), drawn over `gblur` of the whole frame. The x/y expression holds on a subject change (cut) and interpolates on a gradual move (pan) - the "auto by content" rule: a podcast cuts between speakers, a sports follow pans with the play. The optional inset is a 420x236 16:9 crop with a white border, taken at 42% of the source height (`pipZoom`) so the event inside it is readable rather than half the frame; it is placed bottom-right, or bottom-left when the mean main-subject cx is > 0.5, and shown only during pip windows through `enable='between(t,a,b)+...'`. `track[]` points that carry `cx2/cy2` inside a pip/split window drive camera 2 over time (a window-level point alone would freeze the inset while the second subject walks away); camera 2 uses a wider snap tolerance (`secSnapAt` 0.35 vs 0.10) so it pans after a moving subject and only cuts on a real jump. The optional split layer is two 1080x960 crops stacked with a 6px dark divider, shown only during split windows. ## 4. Shared job lifecycle

All long-running pipelines use the in-memory job registry and SSE helpers in `server/jobs.js`. Cancellation/abort behavior is a cross-cutting contract. Any change to jobs/SSE requires checking all three pipelines plus the YouTube import job. Unique, Edit, and Reframe do not set `killTree`, so cancel still sends one `SIGKILL` to `job.ffmpeg`. A YouTube import job sets `killTree`, so cancel kills that child tree (`taskkill /T /F` on Windows, `kill(-pid)` on POSIX). Import spawns omit Node's `timeout` option; a timeout would kill only the direct child.

## 5. External processing

FFmpeg/ffprobe perform media probing, transforms and encoding. Python is used for PGD/OpenCLIP and local diarization. Google/Gemini/Vertex integrations require credentials/network and may incur quota/cost; do not run them merely as validation.

Those profiles live in the browser key `gf_youtube_concat`. API keys are not in that copy. An idle Unique or Edit tab starts at once. A busy tab queues the clip and leaves the running profile alone. Before Unique or Edit, `POST /api/youtube-import/hold` copies the joined file into the import directory, so a later delete removes only that copy. A file outside the 1000-entry window has no number until a scan includes it.

The anchor name, a receipt row, and the “mở” control beside a concat number open `https://www.youtube.com/watch?v=<11-char id>` in a new tab. The number button only chooses the join order. Save and clear stay buttons. An id that is not 11 characters is plain text.

Quality is `best`, or a ceiling of 144, 240, 360, 480, 720, 1080 (default), 1440, 2160, or 4320. The ceiling is yt-dlp `res:`, the shorter side, so 1080p on a Short is 1080×1920 and 1080p on a landscape video is 1920×1080. Do not cap with `height<=`. H.264 is preferred when that size has it. A higher size that YouTube only offers as VP9 or AV1 is still that size, remuxed to mp4. `best` is the highest size.

The YouTube tab is its own screen. The panel stays mounted and is hidden on other tabs, so leaving YouTube does not close the stream or stop the queue. A reload reattaches Hủy from `active.jobId` and continues any URLs still in `gf_youtube_batch`. `save` sets `removeSource` so the copy route deletes the import directory after the copy. That route is used instead of `DELETE`, because `DELETE` returns 409 while the stream is still closing. Unique and Reframe still call `DELETE /api/youtube-import/:jobId` once their own job has closed the file, and they keep `removeSource` false so the import file remains until then. Edit does not delete the import directory: part replay stores that path. The chosen-folder copy is a separate file and stays. Do not sweep `uploads/youtube-import/` at boot.

`POST /api/unique/job-local` is only the disk entrance for Unique (`keepInput: true`, no `kind`). `GET /api/stream/:jobId` still encodes it. A successful Unique run also unlinks `inputPath` before `done` (the pre-existing encode cleanup). `keepInput` only blocks `DELETE /api/job/:jobId`. The UI delete then removes the import directory. Do not point `job-local` at a file that must survive a successful Unique run. Edit and Reframe never take that Unique unlink path.
