# AI and external integrations

## TikTokApi hashtag videos

The optional direct hashtag endpoint can enumerate videos when TikTok accepts automated requests. The Trends panel instead filters its loaded Creative Center top-video list and links to TikTok for full hashtag browsing. The Node adapter runs `tiktok_hashtag_search.py` with `GHOSTFORGE_TIKTOK_PYTHON`, then the repo's ignored `.venv-tiktokapi/Scripts/python.exe` if present, then `GHOSTFORGE_PYTHON`/`python`. Install Python 3.9+, `pip install TikTokApi`, and `python -m playwright install chromium` in that interpreter. A TikTok.com `msToken` is required: run `.venv-tiktokapi\Scripts\python.exe scripts\tiktok-api-session.py`, complete access in the visible browser, then press Enter in the terminal. An account login is not intrinsically required for public hashtag video enumeration. The setup script fails immediately if TikTok returns HTTP 403; no session can be saved from a denied page. The ignored `.tiktok-api-session/storage-state.json` holds successful cookies; `TIKTOK_MS_TOKEN` can override the token. Do not commit or share this session file. TikTokApi's `search` module currently supports users only, so this is not free-text video search. TikTok can still block automated access with a valid token. It has no country/date filters. The lookup is read-only and independent of Creative Center sessions and their `.tiktok-session/` profile. On this machine the user passed CAPTCHA and saved an `msToken`, yet TikTokApi still returned an empty response in headless, headed, and persistent-profile requests; the Creative Center video list remains the working path.

When Playwright Chromium is denied but an ordinary browser profile works, run `scripts/tiktok-api-session.py --manual-token` from a local terminal and enter the `msToken` cookie value from that browser's TikTok.com cookies. The prompt hides the value; never paste it into chat. The bridge sends TikTokApi a list containing one cookie name/value mapping, as its `create_sessions` implementation expects. On this machine the user's working browser profile is Opera GX `Family security`. A token does not guarantee that TikTok will permit automated API calls; test one read-only hashtag request after saving it.

## Gemini / Vertex
GhostForge contains both Gemini API/file-upload paths and Vertex AI paths. Edit and Auto Reframe have separate planning helpers. Credentials/models come from runtime settings/environment; secrets must not be committed to documentation or fixtures.

Gemini key storage (2026-10-01): the account list and the chosen model persist in `uploads/gemini-keys.json` through `GET/POST /api/gemini-keys` (`server/gemini-secrets.js`). The browser localStorage copy is only a cache - it is per origin, which is why the keys used to disappear after the app was opened from another port/profile or after clearing site data, and it was only written when a run started. `GHOSTFORGE_SECRETS_FILE` relocates the file outside the repo. The file holds live secrets in plain text and is gitignored; nothing logs the values.

Per-part Detail on the focus path (2026-10-01, model order 2026-10-02): Detail ALWAYS runs on the focus path (`mode=ai`, no TEST, no switch - operator decision) and re-watches each cut part with `focusDetailPrompt`: **one extra AI call per part, through the Gemini API key when one is entered, and Vertex only as the fallback when there is no key**. So Global plan = Vertex ADC (1 watch of the whole video) while Detail = the Gemini API, which is the split to keep in mind when reasoning about quota. The API-key model order is the `MODEL DETAIL (API KEY)` select (`detailModelMode`): **`safe` (default) = the measured ladder starting at `gemini-3.5-flash-lite`, then 3.1-flash-lite, 3.5-flash, 3.8, 3.6, 3.7**; `quality` = the model chosen in the MODEL box first, ladder as fall-back; `only` = that model alone. The lite-first default is not an oversight: the 2026-09-23 eleven-video log measured 3.5-flash-lite at 41 plans / 0 overloads while 3.8 / 3.6 / 3.7 were overloaded on nearly every attempt (2 / 2 / 0 plans against 11 overloads each), and a video once spent ~7 minutes re-calling refused models. What makes `quality` usable now is `createOverloadCache` in `server/detail-models.js`: a model that answers "high demand" is skipped for 10 minutes by every job in the server run, so the operator pays one fast failed call per dead model per 10 minutes instead of one per part. Detail is what turns a 5-window whole-video plan into an 11-window (and up to 34-window) per-shot plan on real footage, so a part no longer sits on one static crop.

Edit prompts (2026-10-01): the default Edit framing is now `framingStyle=focus`, which plans with `focusEditorPrompt` (one global Vertex call, same model selection as before) instead of the SML system prompt. It is topic-agnostic, embeds the operator's own prompt text as "Operator request" rather than dropping it, and asks for `focus` / `pip` / `split` windows with `cx,cy` for the main subject and `cx2,cy2` for a second event worth a corner window or a top/bottom split. Two extra rules came out of the live runs and are what actually make `pip` fire: two subjects more than ~1/3 of the frame width apart must be pip/split rather than focus, and a reaction/commentary face camera in a corner must become the corner window instead of being cropped away. `generalGlancePrompt` (quiet parts) returns the same focus/pip/split vocabulary, so no part of the default path can come back asking for a letterbox. This adds **no** AI request: the plan is still one global call per video, there is no per-part Detail on the focus path, and Google STT + pyannote still run over the whole video and only supply who/where for the crop. `focusDetailPrompt` is used only by TEST / Test lại Part on the focus path; the SML prompts (`editorSysPrompt`, `detailSemanticFramingGuidance`) are unchanged for `framingStyle=sml`. The quiet-part glance stage is gated on `mode=ai` (so `mode=even` performs no AI call at all) and only FILLS IN for a part whose global plan produced no frames - it no longer replaces the plan's framing, which also removes a Vertex call per part in the normal case. Verified live on Vertex 2026-10-01 (police bodycam, wildlife, reaction video): the model returns 5-6 focus windows per part on cops footage and chose `pip` on its own for a streamer-facecam layout; measured plan cost 33.8-120.2 s on a 276 s source (one inline-timeout retry at 348 s).

Detail JSON is asked for with `maxOutputTokens` 65536 and the lowest supported thinking level, because thinking tokens and the visible sheet share that limit. A track point is requested about every 0.4 seconds during fill, and again at the instant the speaker or face changes. The 65536-token cap is what keeps that longer sheet from being cut off. `finishReason=MAX_TOKENS` is logged with the candidate and thought token counts.

Cost and model accounting (2026-10-03): the recorded `model` in the QA history is the UI preference, not the model that answered - with `detailModelMode: safe` the ladder usually answers on `gemini-3.5-flash-lite` even when the box says `gemini-3.8-flash`. Every successful API-key call now stores the provider's `usageMetadata` in `job.geminiUsage` (`recordGeminiUsage`, labels per call site) and also logs the real id (`[EDIT] Detail 1/3: model thật gemini-3.5-flash-lite · 6440 in (cache 0) · 671 out · 94đ`); `done.report.geminiCost` totals it in VND via `server/gemini-cost.js`. Billed-but-discarded answers (`MAX_TOKENS`, empty text) are counted by riding the usage on the error; 429/503 are not billed and not counted. Measured rates for the production proxy (854p/12fps/mono) on `gemini-3.8-flash`: ~104 input tokens and ~32 output tokens per second of kept video, and implicit caching returned `cachedContentTokenCount` 3516 on the coverage re-ask (billed at the cache-read rate). `mediaResolution` made no difference to the token count (`MEDIA_RESOLUTION_LOW` gave the same 6245 prompt tokens), so it is not a saving lever. Vertex usage is deliberately not included. Free-tier keys are charged 0 USD but still consume quota.

Targeted Part replay follows the current Edit output checkboxes. With Mixed 9:16 off, the replay skips Detail and speaker/STT analysis; TikTok pad alone only adds the existing visual pad. With both output options off, the selected original-source excerpt is returned at source aspect ratio without Detail/STT/diarization.

Quota rule for agents: do not call live Gemini/Vertex as a routine test. First use static inspection, unit tests, syntax checks, targeted mocks/logging, or targeted-part mode. When investigating quota, enumerate every reachable AI call for the exact settings before proposing a fix.

Global Edit's existing video request asks for top-level `excludedRanges` (`start/end`, `kind: outro|advertisement`, `confidence: certain`, concrete observed `reason`) plus `tailEvidence` (`storyEnd`, `outroStart`, `reason`). Only unrelated advertising/end-card content may be excluded; in-story props/product jokes/dialogue must stay. Missing/invalid/uncertain evidence keeps the footage automatically before Detail. This adds no AI request and does not change Detail/TEST prompts, model or quota policy. Self-reported evidence can still be mistaken; conservative retention may include an outro/ad when uncertain.

## Google Speech-to-Text

Edit can use Google STT word timing. Retry/chunk behavior is partly isolated in `server/google-stt-retry.js`; orchestration is in `googleSttWords` in `ghostforge-server.js`. Edit does not pass a language and stays `en-US`.

Unique captions (switch `enableCaptions`, default off) call the same helper after one local faster-whisper pass. The 6th argument `{ languageCode, logTag }` selects the language. `server/unique-extra.js` `googleLanguageCode` maps the whisper code (`pt` → `pt-BR`). The burn keeps the whisper clock. A Google word replaces the spelling only when `alignCaptionWords` treats the two words as the same beat. Google word times are not burned. The listener is `caption_words.py`: faster-whisper small, CPU int8, via `.venv-diar` unless `GHOSTFORGE_CAPTION_PYTHON` is set. CUDA is not used for this pass. A whisper or Google failure keeps the Unique file.

## Local diarization
`local_listen_diarize.py` is invoked by `runLocalDiarization`. Mapping/ambiguity handling is in `server/local-listen-map.js`. Default interpreter lookup uses `.venv-diar/Scripts/python.exe` unless `GHOSTFORGE_DIAR_PYTHON` is set.

## Experimental Local Detail

The opt-in 30/60s Edit TEST can use a project-private Ollama runtime on `127.0.0.1:11435` with `qwen3-vl:2b` Q4_K_M. Runtime/model data live under ignored `.local-ai/`; current target machine is RTX 3050 Laptop 4GB VRAM, i7-12800H and 32GB RAM. The request sends chronological JPEG samples with timestamps/scene-cut reasons, uses JSON mode and temperature 0, and accepts Qwen's JSON from Ollama `message.content` or `message.thinking`. The schema allows one segment, at most 8 frames and 16 track points, with short summary/why strings. An empty track is allowed for frames with sufficient position data or CONTAIN; a FILL without frame coordinates or an in-window track point is rejected. Excerpt timing is not passed through the production minimum-part gate. Adjacent identical sub-second windows are coalesced. It is visual-only: no audio, Vertex/Gemini, Google STT or Local Listen, and no cloud fallback. A real 30s 9:16 render completed on 2026-09-22; the 2B model still emits repeated short windows, and one surviving window falls through to mix scene fallback.

## PGD / OpenCLIP

`pgd_clip.py` uses Python/PyTorch/OpenCLIP. `pgd_server.py` loads that same ViT-B-32 once per server run. Backend interpreter selection uses `GHOSTFORGE_PYTHON`, then `.venv/Scripts/python.exe`, then `python`. `/api/pgd-status` provides a readiness check. The attack loss matches the pool-4 residual written into the file.

Two opt-in flags exist for robustness experiments and change nothing by default: `--eot-mode jpeg|codec|ladder|mix` (default `jpeg`, the shipped jpeg/resize stack) picks which transforms EOT trains against, and `--pool-size` (default 4) sets the residual averaging factor; the warm `pgd_server.py` forwards `eotMode` from a request. `GHOSTFORGE_CLIP_WEIGHTS` is an operational escape hatch: when it points at a local `.safetensors`/`.pt` ViT-B-32 checkpoint, `load_clip_pack` loads from that file instead of the Hugging Face hub, which matters on a host whose HF cache is read-only or whose hub is unreachable. Measured effect of the flags, and what survives a TikTok-like re-encode, is in `docs/transcode-robust-unique.md` §8b.

Measured on this machine 2026-10-01: `pgdPython()` resolves to `C:\Users\T15p\AppData\Local\Python\pythoncore-3.14-64\python.exe` (3.14.7) through the `%LOCALAPPDATA%\Python\bin\python.exe` shim, and that interpreter has `torch 2.11.0+cu128`, `open_clip 3.3.0`, `numpy`, `Pillow` and working CUDA on the RTX 3050. It loads `hf-hub:laion/CLIP-ViT-B-32-laion2B-s34B-b79K` from the local HF cache in ~1.6 s, and still loads in ~1.1 s with `HF_HUB_OFFLINE=1` (the cache holds `open_clip_model.safetensors`; the 604-byte `open_clip_config.json` is not cached and is not required). So the model load does not depend on the hub being reachable on this host. Launch the app from `start.bat`/a normal shell: a stripped PATH makes `pgdPython()` fall back to a bare `python` that may not resolve, and then PGD fails while Unique still succeeds.

Attack cost measured 2026-10-01 (60 s 1080x1920 excerpt, 1801 frames, 121.6 s): the attack loop 96.2 s, read + yuv→rgb + downscale 1.7 s, rgb→yuv + numpy 7.2 s, waiting on decode 0.7 s, writing to the encoder 1.3 s; FFmpeg alone (decode + NVENC qp18 full-res encode) is 10 s. `--amp bf16` is faster with the same result (in-attack mean CLIP 0.7109 vs 0.7095 float32) and `--adaptive-skip` only helps static footage. Since 2026-10-01 the app sends `amp: 'bf16'` and `frameStep: 2` with every PGD request (`runPgdClip` -> `pgd_server.attack_argv`), so production PGD is bf16 and attacks every second frame; `adaptiveSkip` and `phashLoss` are forwarded but stay 0, and the Unique tab's default level is now `strong`.

`--phash-loss <weight>` (default 0) adds a differentiable DCT-pHash term (`soft_phash`: 32x32 downsample, 8x8 low-frequency block, DC dropped, coefficient minus block mean through tanh) beside the existing soft-dHash `--hash-loss`. Measured 2026-10-01 on a 16.46 s clip at strong/bf16/frame-step 2: pHash after the platform re-encode goes 0.26 % (off) -> 1.32 % at weight 2 -> 2.38 % at weight 5, while post-re-encode CLIP worsens 0.7917 -> 0.8055 -> 0.8192 and the wall time does not change. It cannot make a hash match fail (the Unique layer already moves pHash 34.9 %) and it costs embedding protection, so it stays off.

## FFmpeg
FFmpeg/ffprobe are runtime dependencies. Encoder probing supports CPU/libx264, NVIDIA NVENC and Intel QSV fallback logic. Do not modify encoder/filter behavior during unrelated refactors.

## Environment assumptions
The application is local-first and contains Windows-specific folder/explorer/Python-environment behavior. The provided package may have Windows-installed dependencies; Linux agent sandboxes may require a clean dependency install to build Vite. See `VALIDATION.md`.
